# Fault management and dynamic rescheduling design

Status: implemented offline on feat/fault-recovery following the user's instruction
to implement this plan. Verification and preview evidence are in docs/development.md.

## Goal and boundaries

Safely isolate simulated printer faults, recover unfinished approved work on healthy
printers, and explain the resulting production and customer-order impact. Preserve
completed output, healthy active prints, consumed stock and the current application
architecture. An incident must remain understandable after a refresh or restart.

The user requires thermal faults, filament runout and network disconnections.
[SPEC.md](../../../SPEC.md#faults-and-recovery) and PA-401 additionally require nozzle
clog and insufficient material; include all five with explicit simulated effects.
Website/model import integration remains partner work. No hardware adapter, remote
shop, continuous inference, live agent invocation or physical safety claim is added.

## Inspected foundation

- `FactoryService._transition` already serializes changes using a lock, SQLite
  transaction, source session/revision checks and idempotency receipts.
- `Store` persists a JSON state snapshot, so additive incident/report fields do not
  require replacing storage or introducing another service.
- `scheduling.py` dispatches idle compatible printers; `proposals.py` plans future
  slots from priority, deadlines, availability and remaining material commitments.
- `simulation.py` consumes filament progressively and increments successful output
  only on completion. Currently insufficient filament raises an error rather than
  producing an incident, and the service can stop the clock globally.
- `reservations.py` derives commitments from active attempts. Failed work must leave
  that active set without refunding material already consumed.
- `monitoring.py` projects completion and telemetry. Manual/held work can have an
  unknown completion; comparisons must preserve that uncertainty.
- The dashboard already has printer fault coloring, an order-colored timeline,
  activity events and shared typed production commands. There is no injection,
  incident report, recovery proposal or functional orchestrator/agent gateway yet.

## Approach and implementation choices

Extend the existing pure transitions and transactional service. Add focused incident,
recovery and schedule-impact modules, retaining the current planner as the authority.
A separate event bus or optimization service would add state coordination without
helping a three-printer offline demonstration. An LLM-directed dispatcher would make
safety and repeatability dependent on inference; it is not the recovery authority.

Implementation choices retained from the reviewed plan:

- Require operator review by default, matching the existing spec.
- Offer a separate opt-in simulation recovery policy for complete, compatible,
  on-time plans. Default it back to review on startup/reset, independently of the
  Agents Enabled and automatic-agent-trigger switches.
- Never clear or restart a faulted printer automatically. Recover production onto
  healthy equipment; explicit simulated repair/refill clearance is a separate action.
- Automatically escalate incomplete, late, manual-start or otherwise uncertain plans.
  An operator may explicitly accept a feasible late/partial plan with its risks shown;
  no-feasible-assignment plans remain blocked with mitigation options.
- Use deterministic priority/deadline ordering and earliest feasible finish with
  stable tie breaking. Document this as a scheduling heuristic, not proof of a
  globally optimal manufacturing schedule.

## Event and safety lifecycle

Injection uses a typed command containing printer ID, fault type and a unique source
event ID. Fault events generated by simulation boundaries use the same domain path.
Capture the current schedule immediately before isolation in the same transaction.
Then stop the affected printer before planning recovery or producing explanation.

An incident records its ID, source event ID, simulation timestamp, printer, type,
affected attempt IDs, telemetry and equipment state. Duplicate event delivery returns
the existing outcome; another command against an already isolated printer cannot
restart work or create duplicate replacement attempts. An event with conflicting
identity is rejected visibly. Repeated real faults after valid clearance create a
new incident while preserving previous history.

| Fault | Immediate simulated effect | Clearance prerequisite |
| --- | --- | --- |
| Thermal | Stop motion/heating and mark equipment faulted; retain fault reading and isolated/cool-down telemetry separately. | Explicit simulated inspection/cool-down acknowledgement. |
| Filament runout | Stop feed/printing; mark interrupted output failed and record consumed material. | Explicit refill with positive known stock. |
| Network disconnect | Conservatively stop simulated production and mark connection unavailable. | Explicit simulated reconnection/inspection. No physical connectivity guarantee. |
| Nozzle clog | Stop printing and retain failure/waste history. | Explicit simulated maintenance acknowledgement. |
| Insufficient material | Block dispatch or stop at the exhaustion boundary; never permit negative stock. | Explicit matching material refill or reschedule elsewhere. |

Model thermal and connection readings explicitly; do not derive healthy-looking
telemetry from a faulted status and overwrite the original evidence. Injection of
runout may correct the demo inventory to zero; record that stock adjustment separately
from failed-print waste so missing spool inventory is not counted as printed scrap.

Split simulation advancement at completion and material-exhaustion boundaries. A
fault stops only affected work; advance healthy work for the remaining interval.
Never roll back healthy completed progress or stop the entire fleet for a local fault.

## Work and material accounting

- Completed attempts and `successful_quantity` stay unchanged by a fault/replan.
- An interrupted attempted part is failed, with consumed grams retained as waste;
  its replacement needs full model duration and filament. A disconnected print is
  conservatively restarted rather than silently resumed without inspection.
- Unstarted queued parts may move without becoming scrap. Preserve their identity
  and compare their old/new assignments. Keep historical failed/cancelled attempts.
- Add optional part lineage (`part_key`, `replaces_job_id`) for retries. Legacy
  attempts can use their existing ID as the part key; repeated retries keep it.
  Quantity checks use successful output and outstanding parts, never attempt count.
- Hold the affected unfinished approved workload until a recovery is applied or
  explicitly resolved. Ordinary dispatch must not create replacements while review
  is pending. Existing healthy active work and its reservations remain protected.
- Enforce that hold at every production entry point: clock ticks, ordinary scheduling,
  reviewed normal schedules, manual starts and printer controls. A generic schedule
  confirmation must not erase an incident hold or authorize a failed part's retry.
  Healthy existing unheld work can continue; an approved recovery creates explicit
  authorization for its replacement parts rather than reopening the whole order.
- Give every held part exactly one owning incident. A recovery proposal targets one
  incident and enumerates its owned parts. If another printer fails on the same
  customer order, its parts remain separately held. Applying, rejecting or clearing
  one incident never releases the other's parts, waste or history. Shared-order
  completion stays unknown while another required part remains unresolved. A new
  fault invalidates any older proposal through revision/fingerprint guards.
- Include movable healthy queues in a recovery when useful, so urgent replacement
  parts can change other orders' completion. Do not approve new inbox/held quantities
  implicitly or change manual jobs into automatic starts without explicit approval.
- Validate remaining physical stock, committed stock and model compatibility again
  at apply time. Consumed stock is never refunded or subtracted twice.

## Recovery proposals and atomic execution

Generate a read-only typed proposal from current state, incident and policy. Include
session/revision, a deterministic fingerprint, preserved active attempts, movable
attempts, replacement lineage, assignments, blocked parts, impacts, assumptions and
mitigations. The preview does not reserve stock or modify manufacturing state.

Revalidate the exact proposal before application; reject stale state, reset sessions,
changed stock, conflicting approvals and duplicate/conflicting part allocation.
Apply queued assignment changes, replacements, material commitments, order holds,
incident actions and production scheduling in one existing service transaction.
Preserve per-order start mode and execute queued work in planned sequence. Reassigned
automatic jobs dispatch as compatible healthy printers become available.

Automatic policy application uses the same validator and transaction. It cannot
waive compatibility, safety, quantity, stock or deadline gates. A rejected review
leaves the incident and equipment isolation intact and permits a later fresh proposal.
No background LLM retry loop is introduced.
Normal previews are read-only and transient. Persist proposal versions with their
explicit apply/reject decisions; do not write incident history merely by fetching
a preview. Retain initial diagnosis and the immutable pre-fault snapshot immediately.

## Before-and-after schedule impact

Store an immutable pre-isolation schedule, the proposal's revised schedule and the
actually applied schedule. Later actual outcomes/projections are labeled separately
so ticking, retries or repair cannot rewrite the original comparison. Use absolute
UTC simulation timestamps and report delta only when both estimates are known.

For each part/attempt, retain order and lineage, old/new printer, start and finish,
remaining/restart duration, material requirement and action (preserved, moved,
restarted or blocked). Link failed attempts to replacements rather than comparing
unrelated newly generated IDs. Show unallocated required parts explicitly.

For every customer order in the schedule, compare:

- original and revised completion (latest completion of all required parts);
- signed completion change, production deadline and late/unavailable risk;
- original/revised printer assignments and outstanding quantity;
- direct interruption versus indirect queue delay, or unchanged work;
- failed-print waste, with incident totals reconciled to affected attempts;
- actions such as refill/repair, additional compatible capacity, later deadline,
  reduced remaining quantity or an explicitly supplied faster prepared profile.

Never claim whole-order completion from partial slots. Preserve completed-part times
and completed quantities. Keep unaffected and indirectly affected orders available
in the comparison; emphasize changed or at-risk ones. Playback acceleration is not
a manufacturing mitigation. Changes to quantities/dates require their existing
explicit workflows, not silent recovery edits.

## Persistent reporting and frontend

The incident report persists diagnosis/evidence, equipment state, affected attempts
and orders, waste, proposed/applied actions, immutable schedule comparisons, current
recovery progress and outstanding operator actions. States distinguish awaiting
review, blocked, rejected, recovering, production restored and fully resolved.
Production can be restored on other printers while the original printer still needs
repair; do not call equipment repaired just because an order completed elsewhere.

Add an **Incidents & Schedule Impact** panel to Overview with an inspectable history
and compact risk/progress summaries. Keep detailed comparisons in a selected incident
view. Floor cards show isolation/fault cause; printer details provide injection and
guarded clearance. Schedule/timeline show reassigned queues and revised estimates,
retaining order colors and readable warnings. Review and confirmation are keyboard
accessible and bound to the incident's source session/revision.

Provide a concise natural-language operational summary and business impact in the
panel and activity stream using deterministic templates while agents are disabled.
Label its source honestly. The planned orchestrator can later consume the same typed
incident/proposal/report tools; this phase does not claim live AI orchestration.
